\section{Feci Guard: an external verifier}
\label{sec:guard}
If the model does not separate a false ``done'' from a true one, the check has to come from outside, and it should judge the final state rather than the agent's account of it, as $\tau$-bench does by scoring the final database state \citep{yao2024taubench}. Feci Guard is the simplest form of that check. When the agent calls \texttt{answer}, unless the answer declares the task infeasible, the guard takes a fresh screenshot and asks a separate verifier model to list every requirement of the task, to mark each one as met, unmet or not visible with its evidence, and to return a verdict. An \textsc{incomplete} verdict, which requires at least one requirement visibly unmet, refuses the answer and returns to the agent, as the answer's tool output, the missing requirement and a next action; the episode continues. A \textsc{complete} verdict, a timeout or an invalid output lets the answer through. At most two answers are refused per episode, and the third passes unchecked. A refusal always says what is missing, because blocking a false ``done'' without an explanation repaired none of the feasible false successes of the branching pilot (\S\ref{sec:online}). The verifier (Claude Sonnet through the Claude Code CLI, a fixed prompt and JSON schema, a 55\,s timeout) and the decision rule were frozen and registered before any evaluation. % source: data/local/feci_guard/README.md, PREREG.md (verifier sha256 0af76fdbacc72317...)

\paragraph{Offline, the verifier separates false from true successes.} On the same \gbEpisodes{} episodes of the original agent, judged from the final screenshot only, the frozen verifier detects \gbClaudeDet\% of the false successes and rejects \gbClaudeRej\% of the true ones, a gap of \gbClaudeGap{} points (95\% CI \gbClaudeGapCi, bootstrap over \gbTasks{} tasks; Table~\ref{tab:guard}). Holo-3.1-4B judging the same episodes detects \gbHoloDet\% and rejects \gbHoloRej\% (gap \gbHoloGap, \gbHoloGapCi), not distinguishable from chance, and the paired difference between the two judges is \gbClaudeVsHolo{} points (\gbClaudeVsHoloCi). A larger model of the same family, Holo4-27B with the same prompt as Holo-3.1-4B, rejects fewer true successes but detects no more false ones (gap \gbHolofourGap, \gbHolofourGapCi). With the verifier's own prompt and rule, Holo4-27B detects \gbHolofourfeciDet\% and rejects \gbHolofourfeciRej\% (gap \gbHolofourfeciGap, \gbHolofourfeciGapCi; \gbHolofourfeciNoVerdict{} calls without a verdict, counted as passes): \gbHolofourfeciVsHolo{} points above Holo-3.1-4B (\gbHolofourfeciVsHoloCi) and \gbHolofourfeciVsClaude{} below Claude (\gbHolofourfeciVsClaudeCi). At equal prompt, Claude's advantage comes mostly from the model; the prompt helps Holo4-27B by lowering its false rejections from \gbHolofourRej\% to \gbHolofourfeciRej\%, partly because its \gbHolofourfeciNoVerdictTrue{} calls without a verdict on true successes count as passes (\gbHolofourfeciRejValid\% on valid verdicts only). What a refusal is worth depends on the base rate. Among the tasks of the \textsc{test} split that the original, served by Modal, closes with \texttt{answer}, \fgBaseFsDone{} score 0 and \fgBaseTrueDone{} score 1 (\fgBasePartialDone{} partial scores left out), a false share $f\approx\fgBaseF$. With the verifier's detection $d$ and false rejection $r$ above, the precision of a refusal, $df/(df+r(1-f))$, is about \fgPrecision: roughly one refusal in four would hit a true success. This is an estimate, since the rates come from neighbouring distributions, not the same one. % source: data/local/online/results_test_gh_orig_modal_test/last_steps.jsonl (extract_last_steps.py), data/local/judge_bench/RESULT.json (figs/guard.py)
This is the measured basis for an external verifier, with three limits. One screenshot cannot show a saved file or a hidden setting, so detection cannot reach 100\%. Each judge ran once. And Claude may have seen public OSWorld tasks. % source: data/local/judge_bench/RESULT.json, REPORT.md (figs/guard.py)

\paragraph{Online, the guard is not yet shown to raise the score.} In one end-to-end episode on a LibreOffice Impress task the original had failed with a false success, the guard refused the first ``done'' because the strike-through stopped mid-word, the agent followed the feedback and fixed the line, and the second ``done'' passed; the official checker still scored the task 0, because the remaining difference lies in the saved file, which the screen does not show. The guard also runs in our side-by-side live demonstration of the original and the guarded agent. A repair measure was registered before it ran: branching \fgRepairEpisodes{} recorded feasible false successes at their final answer, two continuations per arm, with and without the guard, at most \fgRepMaxSteps{} new steps, scored by the official evaluator. Of the \fgRepairEpisodes{} episodes, \fgRepEpisodes{} replay faithfully in every branch of both arms (\fgRepExcluded{} are excluded for replay drift), \fgRepBranches{} branches per arm. With the guard, \fgRepRepairedGuard{} of \fgRepBranches{} branches repair the task, against \fgRepRepairedNog{} of \fgRepBranches{} without it; the guard refused \fgRepRefused{} branches, \fgRepRefusedRepaired{} of which were then repaired. The episode-level paired difference is \fgRepDiff{} (95\% CI \fgRepDiffCi, bootstrap over episodes), better on \fgRepBetter{} episodes and worse on \fgRepWorse; one episode, \texttt{\fgRepBothTask}, is solved in every branch of both arms. The refusal sometimes helps the agent repair, without statistical evidence at this stage. An earlier partial snapshot, five episodes complete, had shown no repair in either arm. We have no OSWorld gain to report for the guard. % source: data/local/rescue_bench/HOLO31_REFERENCE.json contemporary_live_measure (audited), data/local/feci_guard/PREREG.md "Repair measure" (figs/guard.py)
